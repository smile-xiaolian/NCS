# 充电桩通信模拟器（拔高任务）

## 需求说明与技术方案

版本 V1.0 ｜ 定位：NCS 实训项目的**独立拔高模块**，与主工程解耦，可脱离本课程独立复用
适用对象：15 个小组中进度领先、有余力的组（建议 2-3 组或组内 1-2 人抽调攻坚）

---

## 0. 价值点

**跟主工程的关系**：主工程（见《02-系统设计说明书》第2.2节）里"充电"是 `client_user` 进程内部一个状态机，靠 `time_scale` 模拟时间流逝，**没有真实的"桩"和"平台"分离通信**。本模块是在这个基础之上**另起一个独立子项目**，不改动、不依赖主工程代码，用来补足"真实充电桩行业里设备到底是怎么和管理平台通信的"这一课——这一课在主工程里是学不到的，但恰恰是这个行业里最值钱的部分。

**技术上可迁移**：这套东西的核心不是"充电桩"，而是三个通用能力——
1. 设计一套请求-响应式的消息协议（真实 OCPP、MQTT 场景下的物联网设备通信都是这个模式）
2. 处理连接生命周期（断线重连、心跳超时判定离线）
3. 管理并发多连接（一个平台同时管理多个设备）

这三点跟具体是"充电桩"完全无关，换成电梯监控、自动售货机、任何"许多台设备连一个中控平台"的场景都能直接套用下层框架。这是一套**架构模式**，不是"充电桩"这个业务本身。

## 1. 设计原则：分层解耦，下层框架必须与"充电桩"无关

```
┌─────────────────────────────────────┐
│  上层：充电桩业务逻辑                    │  ← 这一层认识"充电桩"
│  （消息定义、桩状态机、平台业务处理）        │
├─────────────────────────────────────┤
│  下层：通用设备通信框架 device_link_core  │  ← 这一层完全不认识"充电桩"
│  （连接管理、心跳、重连、消息编解码、       │     只认识"设备ID + 消息 + 回调"
│   请求-响应关联、多连接管理）             │
└─────────────────────────────────────┘
```

**验收这个设计原则**：下层 `device_link_core` 目录里如果出现"充电""电量""桩"这些字眼，就是设计错了——下层只应该有 `DeviceConnection`、`MessageFrame`、`ActionDispatcher` 这类通用词汇。

## 2. 功能需求

### 2.1 角色与连接方向

- **PlatformSimulator**：`QWebSocketServer`，监听固定端口，同时接受多个设备连接（模拟真实场景里一个平台管多个桩）。
- **PileSimulator**：`QWebSocket` 客户端，启动后主动连接平台。**连接方向不能反**——真实世界里设备主动连平台，不是平台去连设备（平台不知道设备在哪、有多少）。

### 2.2 消息集合（简化版，覆盖核心交互闭环即可，不追求还原完整 OCPP）

采用**类 OCPP 的数组格式**（不是严格 JSON-RPC 2.0）：

```
请求：  [2, "消息唯一ID", "Action名称", {payload}]
成功响应：[3, "消息唯一ID", {payload}]
失败响应：[4, "消息唯一ID", "错误码", "错误描述", {}]
```

| 方向   | Action                 | 说明                            | 触发频率       |
| ---- | ---------------------- | ----------------------------- | ---------- |
| 桩→平台 | BootNotification       | 桩上线注册，携带桩编号、型号                | 连接建立后立即发一次 |
| 桩→平台 | Heartbeat              | 心跳保活                          | 每 10 秒     |
| 桩→平台 | StatusNotification     | 状态变化（Idle/Charging/Faulted）   | 状态变化时      |
| 桩→平台 | MeterValues            | 上报当前功率、累计电量                   | 充电中每 2 秒   |
| 平台→桩 | RemoteStartTransaction | 下发开始充电指令                      | 用户触发       |
| 平台→桩 | RemoteStopTransaction  | 下发停止充电指令                      | 用户触发       |
| 平台→桩 | RemoteReset            | 远程重启指令（可选联动主工程的"远程重启"按钮，见第6节） | 管理员触发      |

### 2.3 桩状态机

```
Booting → Idle（收到 BootNotification 的 Accept 响应）
Idle → Charging（收到 RemoteStartTransaction）
Charging → Idle（收到 RemoteStopTransaction，或本地模拟"充满"）
任意状态 → Faulted（模拟故障注入）
Faulted → Idle（模拟故障恢复）
```

### 2.4 异常场景（必须做）

| 场景        | 要求                                       |
| --------- | ---------------------------------------- |
| 桩连接断开     | 平台在 3 个心跳周期（30 秒）内未收到心跳，判定该桩离线，从在线列表移除   |
| 桩断线后      | 客户端自动重连，采用指数退避（1s → 2s → 4s → 最大 30s），不能无限快速重试打爆连接 |
| 消息 ID 不匹配 | 平台或桩收到一个响应，但找不到对应的未完成请求，记录警告日志，不崩溃       |
| 平台同时管理多个桩 | 至少支持 5 个桩并发连接，互不干扰，各自独立心跳与状态             |
| 故障注入      | 桩模拟器 GUI 提供按钮，可手动触发"通信中断""设备故障"，用于测试平台的异常处理是否正确 |

### 2.5 GUI 要求（两端都要有界面，不要做成纯命令行）

- **PileSimulator 界面**：显示当前连接状态、桩编号、当前状态（Idle/Charging/Faulted）、实时功率曲线（可以用简单数字滚动代替，不必上 QtCharts）；提供"手动断线""模拟故障""恢复正常"按钮。
- **PlatformSimulator 界面**：一个列表，展示当前所有在线桩及其状态、最后心跳时间；每行提供"下发开始充电""下发停止充电""远程重启"按钮。

## 3. 技术方案

### 3.1 工程结构（独立于 NCS 主工程，可单独成为一个 Git 仓库）

```
device_link_sim/
├── CMakeLists.txt
├── core/                        通用设备通信框架（与"充电桩"无关）
│   ├── MessageFrame.h/.cpp          消息编解码（数组格式序列化/反序列化）
│   ├── ActionDispatcher.h/.cpp      按 Action 名称路由到处理函数
│   ├── PendingRequestTable.h/.cpp   消息ID → 回调 的映射，处理请求-响应关联与超时
│   ├── DeviceConnection.h/.cpp      单个 WebSocket 连接的封装：心跳发送/检测、断线重连
│   └── DeviceRegistry.h/.cpp        平台侧：多个 DeviceConnection 的管理容器
├── pile_app/                    充电桩业务：只认识"充电桩"这个词的地方
│   ├── main.cpp
│   ├── PileController.h/.cpp        桩状态机 + 调用 core 收发消息
│   └── ui/PileMainWindow.h/.cpp     GUI
└── platform_app/                平台业务
    ├── main.cpp
    ├── PlatformController.h/.cpp    维护桩列表 + 调用 core 收发消息
    └── ui/PlatformMainWindow.h/.cpp GUI
```

**这个目录结构本身就是可复用性的保证**：以后如果要模拟别的设备场景，`core/` 目录原封不动搬过去，只需要重写 `pile_app` 对应的业务层。

### 3.2 core 层关键类设计

```cpp
// core/MessageFrame.h —— 只做编解码，不关心消息内容的业务含义
struct MessageFrame {
    enum Type { Call = 2, CallResult = 3, CallError = 4 };
    Type type;
    QString messageId;
    QString action;      // 仅 Call 类型有效
    QJsonObject payload;
    QString errorCode;   // 仅 CallError 类型有效
    QString errorDesc;

    QByteArray toJson() const;
    static std::optional<MessageFrame> fromJson(const QByteArray& data);
};
```

```cpp
// core/DeviceConnection.h —— 通用连接封装，桩和平台两端都能用
class DeviceConnection : public QObject {
    Q_OBJECT
public:
    // sendRequest 发出后返回一个 messageId，超时或收到响应都会触发 callback
    QString sendRequest(const QString& action, const QJsonObject& payload,
                         std::function<void(bool ok, const QJsonObject& result)> callback,
                         int timeoutMs = 5000);
    void sendResponse(const QString& messageId, const QJsonObject& result);

signals:
    void requestReceived(const QString& action, const QJsonObject& payload,
                          const QString& messageId);   // 上层通过 messageId 调 sendResponse 应答
    void connected();
    void disconnected();
    void heartbeatTimeout();   // 平台侧用：超过阈值未收到心跳

private:
    QWebSocket* m_socket;          // 或 QWebSocketServer 传入的已建立连接
    PendingRequestTable m_pending; // 管理未完成请求的超时与回调
    QTimer m_heartbeatTimer;
    QTimer m_reconnectTimer;       // 仅客户端模式使用，指数退避
    int m_reconnectAttempt = 0;
};
```

**设计要点**：`DeviceConnection` 完全不知道"BootNotification""充电"这些词，它只提供"发请求带回调""收到请求转发信号""连接状态变化信号"这几个通用能力。桩和平台各自的业务逻辑（`PileController` / `PlatformController`）订阅这些信号，自己决定收到什么 Action 该怎么处理。这样将来换场景时，`core` 层一行代码都不用改。

### 3.3 心跳与离线判定（平台侧核心逻辑）

```cpp
// PlatformController 里，每个 DeviceConnection 对应一个最后心跳时间戳
void PlatformController::onHeartbeatReceived(const QString& pileId) {
    m_lastHeartbeatAt[pileId] = QDateTime::currentDateTime();
}

// 定时器每 5 秒扫一次
void PlatformController::checkOfflineDevices() {
    auto now = QDateTime::currentDateTime();
    for (auto it = m_lastHeartbeatAt.begin(); it != m_lastHeartbeatAt.end(); ) {
        if (it.value().secsTo(now) > 30) {   // 3 个心跳周期未响应
            markOffline(it.key());
            it = m_lastHeartbeatAt.erase(it);
        } else {
            ++it;
        }
    }
}
```

### 3.4 重连指数退避（桩侧核心逻辑）

```cpp
void DeviceConnection::scheduleReconnect() {
    int delayMs = qMin(1000 * (1 << m_reconnectAttempt), 30000);  // 1s,2s,4s,...封顶30s
    m_reconnectAttempt++;
    QTimer::singleShot(delayMs, this, &DeviceConnection::attemptConnect);
}
// 连接成功后 m_reconnectAttempt 清零
```

## 4. 拆分

| 内容         | 内容                                       |
| ---------- | ---------------------------------------- |
| A：协议与编解码   | `MessageFrame`、消息格式定义文档、单元测试（构造消息→序列化→反序列化→比对） |
| B：连接管理     | `DeviceConnection`、心跳、重连退避、`PendingRequestTable` 超时处理 |
| C：桩端业务与界面  | `PileController` 状态机、`PileMainWindow` 界面、故障注入按钮 |
| D：平台端业务与界面 | `PlatformController`、多设备列表管理、`PlatformMainWindow` 界面 |

建议 A、B 先行（这是下层框架，C、D 依赖它），A、B 完成基础版本后 C、D 并行开发，最后联调。

## 5. 验收标准

- [x] 平台启动后监听端口；启动 3 个以上桩模拟器，平台界面能同时看到全部在线
- [ ] 桩每 2 秒上报 MeterValues（充电中），平台界面数字实时刷新
- [ ] 平台对某个桩下发 RemoteStartTransaction，该桩状态正确切换为 Charging 并开始上报电量
- [ ] 手动断开某个桩的网络（拔线/杀进程模拟），平台在 30 秒内判定该桩离线，界面显示为离线
- [ ] 该桩恢复连接后，能自动重连并重新出现在平台在线列表
- [ ] 消息 ID 关联正确：并发同时向 3 个桩发送指令，每个桩的响应能正确匹配回对应的请求，不串号

## 6. 与主工程的可选联动（不是必须，做完主功能后有余力再做）

主工程管理端"充电桩管理"页面的"远程重启"按钮，当前是**注释里写的"模拟向电桩发送重启指令"**（见《02-系统设计说明书》4.2节），并没有真的发送任何东西。如果这个拔高小组时间充裕，可以做一个**最轻量的挂钩**：管理端点击"远程重启"时，除了原有逻辑，额外调用一个简单的命令行/HTTP 触发接口，让 `platform_app` 真的向对应桩发一条 `RemoteReset`。

**注意边界**：这个挂钩必须做成"主工程完全不依赖它也能正常编译运行"的可选附加项（参考主工程 `NCS_HAS_CHARTS` 的降级思路），不能让 `client_admin` 直接依赖 `device_link_sim` 的代码，否则破坏了主工程的架构解耦，也会给其他 14 个组的编译带来风险。
